# Resume Review (Workflow 1)

**Purpose:** Assess formatting/design, content quality, or job-specific fit, and
return concrete edits.

1. **Scope it.** Confirm which lens the user wants: full review, formatting-only,
   content-only, or against-a-specific-job. Don't over-deliver a 4-section
   teardown when they asked "is my summary too long?".
2. **Load context.** The resume (or its path); if job-specific, the job posting;
   optionally the master docs to check that claims trace to evidence.
3. **Apply standards and score.** Use `references/ats-formatting-standards.md`
   for parseability and `references/resume-quality-rubric.md` for the 0–100
   quality score (or `{{DOCS_ROOT}}/09-resume-quality-rubric.md` if the project
   has its own — that one wins). Check:
   - **Structure:** header, headline (include the target job title — it's the
     single highest-leverage ATS element), executive summary, core competencies,
     experience (reverse-chronological), education.
   - **Bullets:** Action + Scope + Method + Outcome, quantified where the
     evidence supports it. Flag vague claims with no backing.
   - **Tone:** confident, precise, outcomes-oriented.
   - **ATS:** single-column, parseable, standard fonts/headings, no meta text in
     the canonical output (no `Status`, `DONE`, `draft`, TODO notes).
4. **Deliver** concise, specific feedback with edits or rewrite snippets. If a JD
   was provided, include keyword coverage and gaps. When you supply rewritten
   bullets, apply the writing standard and run the critique pass in
   `references/writing-style-and-verbs.md` — vague, AI-sounding rewrites are worse
   than the original.

**Output format:**
- **Summary** (2–3 lines)
- **By section or theme:** what works / what to change / optional rewrite snippet
- **Optional:** requirement-coverage note (only if a JD was provided)
- **Optional:** rubric score (0–100)
